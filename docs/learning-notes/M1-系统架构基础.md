## 1. 系统知识地图

DOVideo-AI 的视频分析主链路可以按两个阶段理解：

1. **任务提交**：Controller 校验请求、用户与媒体；Dispatch 进行活动任务幂等控制、限流并发送 RocketMQ 消息。
2. **任务执行**：Consumer 消费消息、进行结构校验和并发协调，检查已有结果；随后调用 AiService 构建/复用视频上下文、执行 AgentLoop，并持久化结果。

简化图：

```text
HTTP / AnalysisController
        |
        v
AnalysisDispatchService
  | Redis activeKey / quota
  | RocketMQ send
        v
RocketMQ video-analysis-topic
        |
        v
VideoAnalysisConsumer.onMessage
  | message validation
  | Redisson lock
  | attempts / completed checkpoint lookup
        v
AiService.asyncAnalyze
  | load result checkpoint
  | resolveContext (context checkpoint / content reuse / lock)
        v
AgentLoopService.run
        |
        v
AiService.persistResult
  | database update
  | user-list cache invalidation
```

这是主流程抽象；修订任务、毒消息、复用其他媒体上下文、失败转投等分支见对应源码。

## 2. HTTP、Controller 与异步提交

### 2.1 HTTP 语义

- HTTP 202 Accepted 表示请求已被接受处理，不表示耗时业务已经完成。
- HTTP 200 也可能用于已有结果可复用的分支，不能说该接口永远返回 202。

### 2.2 源码映射

**[源码已核实]** `server/src/main/java/com/example/server/controller/AnalysisController.java`

- `aiAnalyze(...)`：约第 101 行起。
- 规范化 goal、解析 AnalysisMode、验证媒体归属。
- 调用 `checkpointService.loadResult(...)`；命中已有结果时返回 HTTP 200。
- 未命中时调用 `dispatchService.submit(...)`，再由 `submissionResponse(...)` 映射响应。

### 2.3 Dispatch

**[源码已核实]** `server/src/main/java/com/example/server/service/AnalysisDispatchService.java`

- `submit(...))：约第 59 行起。
- 通过 `AnalysisTaskKeys` 计算任务身份相关 Key。
- 使用 Redis `setIfAbsent(activeKey, ..., ACTIVE_TTL)` 防止活动任务重复提交。
- 限流未通过时删除本次 activeKey 并返回 RATE_LIMITED。
- 之后调用 `rocketMQTemplate.convertAndSend(...)` 投递消息。

**重要边界：** 发送调用返回不等于消费者处理成功或 Agent 报告生成。还需结合异常分支、消息发送可靠性和业务状态判断。

## 3. RocketMQ Consumer 与任务处理

**[源码已核实]** `server/src/main/java/com/example/server/consumer/VideoAnalysisConsumer.java`

- `onMessage(AnalysisTaskMsg msg))：约第 83 行起。
- 首先调用 `rejectionReason(msg)` 做结构性校验；结构非法消息进入 `discardPoisonMessage(...)`。
- 根据 media、contentHash、goalDigest 构造 lockKey、activeKey、completedKey、attemptsKey。
- 使用 Redisson `lock.tryLock()` 协调并发。
- 获得锁后检查媒体是否存在，递增 attemptsKey 并设置 TTL。
- 普通分析分支读取 completedKey，再尝试加载 Checkpoint 和复用结果。
- 后续调用 AiService 执行分析。

### 3.1 未获得锁时直接返回

源码在未获得锁时记录日志并 return。

**[工程边界/待验证]** 对 RocketMQ Listener 而言，正常返回通常意味着本次监听处理正常结束。不能仅凭“其他消费者可能持锁”证明任务最终一定成功。需结合锁持有者失败路径、Broker 重投行为、任务持久化/补偿机制进行验证。

## 4. Redis Key 的职责

| Key | 源码中的用途 | 注意事项 |
|---|---|---|
| activeKey | 提交时 setIfAbsent；重试时续期；非重试结束时清理 | 表示活动任务去重标记，不等于进程仍健康 |
| lockKey | Redisson 获取互斥锁 | 锁互斥不等于业务幂等 |
| attemptsKey | Consumer 获锁后 increment，并设置 TTL | 应用层尝试计数，不应直接等同 Broker 重投次数 |
| completedKey | 查找已完成结果对应的来源媒体，再加载 Checkpoint | 是快速索引/标记，仍需验证实际结果 |

Consumer 的 finally 分支：获得锁后，只有 `!retrying` 时才删除 activeKey 和 attemptsKey；随后检查当前线程是否仍持锁，再 unlock。

### 4.1 三种机制不要混淆

- **幂等**：防止重复请求/重复消息造成不正确业务效果。
- **重试**：为可恢复失败提供再次执行机会。
- **分布式锁**：协调并发执行者在某段时间内互斥访问。
- **Checkpoint**：复用已保存且对当前任务仍有效的阶段成果。

它们互补，不能相互替代。

## 5. AiService、上下文复用与 Checkpoint

**[源码已核实]** `server/src/main/java/com/example/server/service/AiService.java`

### 5.1 asyncAnalyze

- `asyncAnalyze(mediaId, userGoal, mode))：约第 79 行起。
- 加载最终分析结果 Checkpoint；若结果及 result 存在，则调用 `persistResult` 并返回。
- 否则调用 `resolveContext(...)`。
- 发布 Agent_LOOP 阶段事件，调用 `agentLoopService.run(...)`。
- 成功后调用 `persistResult`。
- 异常时尝试 `checkpointService.saveFailure(...)`；若失败记录写入本身抛 RuntimeException，将其作为 suppressed exception 附加到原异常；BudgetExceededException 保留类型，其它异常包装为 IllegalStateException。

**重要纠正：** 方法名 `asyncAnalyze` 本身不能证明它创建新线程。当前看到的调用发生在 MQ Consumer 处理链中；线程/异步边界需要根据 Listener 容器及具体执行器配置判断。

### 5.2 resolveContext

- 先尝试 `checkpointService.loadContext(mediaId)`。
- 再尝试基于内容的上下文复用。
- 仍未命中时，使用内容级 context lock 协调 ASR/OCR 构建。
- 源码注释明确说明等待锁后要重查 checkpoint，避免并发重复构建。

### 5.3 Checkpoint 与任务状态

| 任务状态/阶段 | Checkpoint |
|---|---|
| 描述任务目前的生命周期/处理阶段 | 保存可恢复或可复用的数据 |
| 面向状态管理和进度展示 | 面向结果恢复与重复计算控制 |
| FAILED 不意味着所有阶段结果都丢失 | 已有 Checkpoint 也不意味着一定有效 |

Checkpoint 可复用前必须确认任务身份、内容、目标、模式及结果有效性。

## 7. 异常传播与恢复

以 Agent 执行阶段 RuntimeException 为例：

```text
AgentLoopService.run
        |
        v
AiService.asyncAnalyze
  | 记录 Agent_LOOP 阶段失败
  | saveFailure（尽力保存失败阶段/异常）
  | 保留 BudgetExceededException 类型
  | 其它异常包装后继续抛出
        |
        v
VideoAnalysisConsumer.onMessage
  | 分类异常
  | 结合业务 attempts 和最大投递策略
  +--> 可重试：retrying=true，续期 activeKey，抛异常交由 MQ 重投
  +--> 永久/达到上限：失败台账、失败主题、任务失败阶段
```

- `saveFailure` 负责记录失败信息，不直接决定是否重试。
- `isPermanentFailure`、attempt 与 Consumer 策略共同参与重试/终止分流。
- 业务 attemptsKey 与 RocketMQ Broker 重投次数不是同一概念。
- 失败台账写入失败时，源码会将记录异常作为 suppressed exception 附加到原始异常。

## 8. 关键设计取舍与待验证问题

### 已理解的取舍

1. MQ 将 HTTP 请求与耗时分析执行解耦，但引入消息重复、失败重试和最终一致性处理成本。
2. Checkpoint 减少重复计算，但必须验证其适用性。
3. 分布式锁减少并发重复执行，但不能代替幂等或任务恢复。
4. activeKey 在重试期间保留，降低用户重复提交的机会；TTL 与异常退出仍需考虑。
5. 结果持久化后失效用户列表缓存，避免继续读到旧摘要。

### 待验证/可形成工程实践的问题

- Consumer 未获得任务锁直接 return 的消息确认语义，和持锁者异常退出后的恢复链是否闭环。
- MQ 投递失败与 activeKey 清理之间是否存在竞态窗口。
- Broker 重投次数、MAX_DELIVERY_ATTEMPTS 和 attemptsKey 在所有异常路径下是否一致。
- 死信主题发送失败时的补偿与重复发送行为。
- Checkpoint、Redis completedKey 与数据库结果之间的失效/恢复一致性。

这些是研究问题，不代表已经证明存在缺陷。需要测试或故障复现后才能作结论。
